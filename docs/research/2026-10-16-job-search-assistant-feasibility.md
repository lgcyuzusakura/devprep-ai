# 求职助手：岗位收集、定向简历与辅助投递可行性研究

研究日期：2026-10-16（北京时间）。对应当前项目源码：`ae3d296`。

已补充第二轮研究：[更多项目、技术文章与工程取舍](2026-10-16-job-search-assistant-deep-research.md)。新增审阅 9 个相关仓库或产品资料，并核对字段映射、浏览器权限、附件、队列恢复及投递幂等性的实现依据；两份报告合计审阅 18 个项目，验证程度见各条说明。

## 结论

可以做，适合作为 DevPrep 的独立“求职工作台”，与现有简历、学习 Agent、模拟面试联动。岗位收集、按 JD 生成独立简历版本、生成沟通话术和管理投递进度，具备明确的实现路径。自动填写与投递也能做，但需要按网站适配，并具备本人登录、异常接管和提交结果核验。

“允许添加任意 URL”可以实现；“任意 URL 均能自动搜索并完成申请”不能据此保证。网站首页、搜索结果页、岗位详情页、ATS 表单页需要不同处理。第一版应明确显示每个来源支持的能力。

推荐沿用 **Spring Boot + React + Docker 主程序，加一个本机 Chrome/Edge 扩展**。现有 Java 后端继续承担岗位、简历、话术、任务及记录；扩展处理用户已登录招聘页面中的读取、附件选择与表单操作。招聘网站账号仍由用户在原网站登录。

本轮只开展资料研究、开源仓库文档及部分源码阅读、两个公开岗位接口的只读验证，没有修改业务代码，没有登录招聘账号、发送话术或提交申请，也没有调用其他模型服务。

## 官方接口：岗位能读取，不等于申请能直接提交

| 来源 | 核实结果 | 产品处理建议 |
| --- | --- | --- |
| [Greenhouse Job Board API](https://developers.greenhouse.io/job-board.html#authentication) | 文档明确：岗位 GET 无需认证；申请 POST 需要 Job Board API Key 的 Basic Auth。 | 可按企业岗位板读取公开岗位；普通求职者通常没有企业密钥，申请使用原站托管表单。不能把公开岗位接口做成全站万能投递 API。 |
| [Lever Postings API](https://github.com/lever/postings-api#apply-to-a-job-posting) | 文档提供岗位列表、详情、`hostedUrl` 和 `applyUrl`。申请 POST 需要账户 Super Admin 生成的 API Key；存在限流与自定义字段。 | 读取岗位后跳转申请页；有合法授权的企业集成才能另做提交 API。官方也建议使用托管表单处理自定义问题。 |
| [Ashby Job Postings API](https://developers.ashbyhq.com/docs/public-job-posting-api) | 公开岗位板返回 JD、地点、发布时间、工作形式、岗位与申请链接，可选薪酬字段。 | 适合第一批公开岗位读取适配器。该文档描述岗位读取，不证明所有求职者均有通用提交权限。 |
| [LinkedIn User Agreement](https://www.linkedin.com/legal/user-agreement) | “Dos and Don’ts” 中限制未授权抓取、浏览器插件采集及机器人访问、发送消息等行为。 | 默认提供链接、手动导入 JD、材料准备与原站申请；没有平台授权时，不列为自动采集/自动消息支持平台。低频并不会自动获得许可。 |

只读接口验证结果：

- `GET https://api.ashbyhq.com/posting-api/job-board/linear`：成功返回 31 条岗位；字段包含 `id`、`title`、`location`、`descriptionPlain`、`publishedAt`、`jobUrl`、`applyUrl`。
- `GET https://api.lever.co/v0/postings/leverdemo?mode=json&limit=1`：成功返回 1 条示例岗位；包含正文、地点类别、`hostedUrl`、`applyUrl`。这是示例岗位板验证，不能据此声称覆盖真实企业投递。

公开接口通常按企业岗位板组织，不能用一个关键词就检索这些 ATS 的全球全部岗位。来源配置应保存企业板名称或企业入口。

## 推荐的实际使用流程

1. **建立求职偏好**：方向、目标岗位、城市、实习/校招/社招、应届年份、经验、学历、期望薪资、远程要求、接受外包与否、排除公司。薪资保留月薪、薪数、币种和实习日薪的原始口径，不直接混比。
2. **添加来源**：内置招聘网站入口；用户添加自定义 URL。保存时识别“导航入口 / 搜索列表 / 岗位详情 / 企业岗位板 / 申请表单”，展示支持读取、填写还是只能手动导入。
3. **收集岗位**：公开接口读取；允许访问的公开页面提取；已登录页面由扩展在用户操作下读取；读取失败则粘贴 JD。保留原网址、时间和完整 JD 快照，支持更正字段。
4. **筛选和解释**：先应用明确的城市、毕业年份等硬条件，再按 JD 与简历证据分析。未知信息标记“待确认”，不能因为模型猜测就丢弃岗位。展示符合项、证据不足和差距，排序理由可追溯。
5. **生成岗位材料包**：每个岗位产生独立简历版本、简短开场白、较完整的自荐说明、必要的求职信和待回答问题。母版不被自动覆盖，关键数据不跨岗位串用。
6. **准备投递**：展示公司、岗位、申请地址、使用的简历文件、消息正文及表单字段；已适配站点辅助填写、选附件。未适配站点提供下载、复制与原站入口。
7. **执行和记录**：第一版逐岗预览确认。若后续增加自动批次，用户事先明确授权岗位范围、简历版本、消息、数量及时间范围；每个任务串行执行，可随时停止。遇到登录失效、验证码、未知字段或页面变化立即暂停。
8. **接续面试准备**：投递记录中的 JD 与已用简历可一键送进现有模拟面试，生成该岗位的八股、算法和项目追问。

话术应围绕“岗位要求 → 简历中哪段经历支持 → 希望沟通什么”，控制长度并可编辑。不能仅把岗位名替换进同一段客套话；岗位要求也不能自动变成用户已经拥有的经验。普通开场、询问岗位细节、发送附件、跟进进度分别生成草稿。对薪资底线、到岗承诺、身份资料等由用户提供事实后再填写。

主程序继续采用模块化单体，不需要因为增加求职功能而引入 LangChain 或多 Agent 服务。

| --- | --- | --- |

| 岗位库 | 岗位快照、搜索、去重、收藏、排除原因、过期状态 | H2/PostgreSQL、Flyway、现有分页与持久化方式。 |
| 岗位评估 | 硬条件过滤、JD 要求与简历证据对应、解释排序 | `ResumeService` 的原材料约束与 JSON 输出校验。 |
| 材料工作区 | 岗位简历、消息草稿、导出文件、材料版本绑定 | `ResumeRepository`、简历诊断/改写、Word/Markdown/PDF 流程。 |
| 投递任务 | 串行队列、暂停/恢复、用户确认、结果与去重 | 新增持久任务状态，模型沿用现有全局请求协调器。 |

建议新增数据对象：`JobSource`、`JobPosting`、`JobAssessment`、`Application`、`ApplicationMaterial`、`ApplicationEvent`。每次提交绑定 JD 快照、简历版本和话术版本；后续改母版不改变历史投递记录。

## Docker 和另一台电脑的迁移

- 现有学习、简历、面试、岗位数据及 GPT 接入继续放 Docker，数据进入持久卷。
- 浏览器扩展安装在用户自己的 Chrome/Edge，连接本机服务。普通公开接口和手动 JD 模式不需要扩展。
- 可选择 Playwright Java 做后续受控浏览器执行验证，但不把 CI 测试中使用的 Playwright 自动等同于生产招聘站已适配。Docker 中运行浏览器也可以实现，首次扫码和交互接管的体验需额外设计，因此第一版优先本机浏览器。
- 扩展与本机服务使用配对凭据，验证来源，限制可操作的站点及标签页。Docker 默认仍绑定 `127.0.0.1`；普通网页不能直接调用本地发送接口。
- 求职网站登录态留在用户浏览器，不放入公共仓库或分发的迁移 ZIP；新电脑需要本人重新登录。模型密钥仍通过 `.env` 配置。

## 投递正确性是主要工程难点

“点击按钮”不能直接算作投递成功。BOSS 这类聊天网站还可能先打招呼，再等待附件发送权限；企业申请页则可能还有确认弹窗、必填问题与验证码。界面应分别显示“已发起沟通”“简历已发送”“申请已提交”。

任务状态建议为：准备材料 → 待确认 → 执行中 → 成功 / 失败 / 需本人处理 / 结果不明。结果不明时先查原站记录，不能自动重试导致重复发送。点击后超时、停止程序或浏览器断开，不代表申请没有提交。

去重优先使用站点岗位 ID；跨平台重复岗位用公司、岗位、地点与原始企业入口做辅助判断，不简单删除同公司同岗位的不同职级。对同一用户同一岗位保存提交尝试和回执，禁止在无提示下重复投递。

还需处理以下与本功能直接相关的问题：

- 某些平台发送的是账户当前“默认附件”，不支持每个岗位临时指定。只有能确认目标附件时才标记支持定向简历投递；不能先改全局附件再并发投多个岗位。
- JD 和网页正文只作为数据，不接受其中的指令来更改任务、读取密钥或发送额外材料。模型输出不能直接获得任意浏览器动作权限。
- 自定义 URL 的后端抓取需限制为 HTTP/HTTPS，校验重定向与目标地址，防止访问本地管理服务、云元数据或内部网络。浏览器助手通过配对通道连接本机，与任意网址抓取分开处理。
- 导入数据、招聘页面片段与真实简历只保存在用户本机；第三方岗位全文不随公开源码发布。把材料发给 GPT 网关的范围应可查看。
- 本轮没有逐家验证国内网站协议，因此“可在浏览器中执行”只是技术判断，后续站点接入必须同时核对使用条件及实际页面行为。用户逐岗确认也不能代替平台许可。

## 分阶段落地建议

**第一阶段：完整求职工作台。** 内置链接、自定义来源、JD 导入、岗位收集和去重、求职偏好、证据匹配、每岗一版简历、中文话术、投递看板、面试联动。加入 Ashby/Lever 等明确的公开岗位读取适配器。所有站点至少能通过手动 JD 完成材料准备。

**第二阶段：一个国内站点的浏览器辅助。** 优先评估 BOSS；若平台条件不允许或关键流程不可稳定验证，则改选支持条件明确的企业 ATS。先做当前页读取、填写、附件核对和逐岗确认，展示回执；不一开始扩展到四个平台。

**第三阶段：扩大站点和可控自动批次。** 每个站点独立维护能力与验收样本，只有已经核实且允许自动化的流程才开放批次。设置数量上限、间隔、排除条件和自动停止条件，复用串行模型队列。邮件投递或自动 HR 回复也作为独立能力，需要另行明确授权发送范围。

工作量主要集中在网站适配与提交结果判定；现有简历和模型模块可复用，但不能据此把完整跨站自动投递估成一个简单页面。建议先对一个站点做可用性验证后再估算整体工期，避免用开源项目 README 的功能列表承诺交付时间或成功率。

## 实施时的验收重点

1. 从一个岗位链接或粘贴 JD，能形成岗位卡片、保存来源及时间；提取失败明确提示补充材料。
2. 每岗生成的简历不覆盖母版，不串用其他公司的名称、JD 或简历附件；导出文件与投递版本一致。
3. 同时发起学习聊天、简历改写和求职任务，外部模型请求仍串行，并遵守全局间隔。
4. 未授权时不能发送消息或申请；确认对应的公司、岗位、简历版本、正文及字段后，才能执行相应任务。
5. 登录失效、验证码、页面字段变化、结果超时和浏览器断开，都有可恢复状态；不盲目重复提交。
6. 仅有按钮点击但没有成功回执时，状态不能记成“申请成功”。
7. 先用自建假招聘表单验证附件、字段、异常、去重和停止；真实站点最后用用户选定的少量岗位验证，不以批量投递充当测试。
8. Docker 新电脑启动时数据为空、凭据自配、招聘站本人登录；Git 仓库与公开发布包均不包含真实求职资料和登录态。
